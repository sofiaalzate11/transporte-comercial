Arquitectura de Software por Capas y Código Limpio

Especificación estructurada por capas con conceptos, tecnologías y patrones.

Proyecto Académico: Transporte y Estado Vial en Colombia

Especificación Técnica por Capas y Patrones de Código Limpio (React Native)
Prólogo Pedagógico: Para garantizar claridad absoluta en el aprendizaje del equipo, este documento organiza cada tecnología, concepto y módulo bajo la estructura canónica de Tres Capas de Software, detallando para cada una: su responsabilidad, los conceptos teóricos subyacentes, las tecnologías oficiales de React Native y los patrones de código limpio aplicados.
Capa 1: Presentación (UI, Navegación y Estado)

1. Responsabilidad de la Capa

Es la capa más externa del sistema. Captura las interacciones del usuario (toques, formularios, navegación) y dibuja la interfaz gráfica (mapa, tarjetas de alertas, estado de envíos). Tiene prohibido ejecutar consultas directas a SQLite o realizar cálculos matemáticos de demoras.

Conceptos Teóricos para Principiantes:
  • El Hilo Principal (Main/UI Thread): La interfaz se refresca a 60 fps en un solo hilo. Todo cálculo pesado debe ejecutarse fuera de este hilo para evitar congelamientos (*Jank*).
  • Renderizado Declarativo: La interfaz describe visualmente el estado: *"Si hay retraso, dibuja la alerta en rojo; de lo contrario, en verde"*.
  • Estado Reactivo en Memoria: Variables que al mutar notifican a los componentes para redibujarse automáticamente sin recargar la pantalla.

Tecnologías y Módulos Oficiales

Tecnología Propósito en la Capa
expo-router Enrutador declarativo basado en carpetas (Pila pública app/(auth) y privada app/(tabs)).
react-native Componentes visuales nativos (View, Text, FlatList, TextInput, TouchableOpacity).
zustand Store de estado global en memoria para la sesión activa del conductor y la ruta seleccionada.
@maplibre/maplibre-react-native Motor de renderizado visual en GPU para mapas vectoriales, polilíneas de ruta y marcadores de incidentes.
Patrones de Código Limpio (Clean Code Patterns):
  • Smart & Dumb Components (Contenedor y Vista): Los componentes visuales (ej. TarjetaIncidente.tsx) solo reciben datos por props; no conocen la base de datos ni las llamadas de red.
  • Auth Guard Pattern: El archivo raíz _layout.tsx valida el token de sesión y destruye de memoria las pantallas privadas si el usuario no está autenticado.
  • Flujo Unidireccional de Datos: Los datos fluyen hacia abajo y los eventos suben por funciones de retorno (callbacks).
Capa 2: Lógica de Negocio y Dominio (Services / Casos de Uso)

1. Responsabilidad de la Capa

Es el núcleo de la aplicación. Contiene las reglas del negocio de transporte: el algoritmo de cálculo de retrasos ($\Delta T$), la detección de cierres viales sobre la ruta y las validaciones de manifiestos. Es 100% agnóstica de frameworks: no importa código de React Native, ni SQLite, ni Axios.

Conceptos Teóricos para Principiantes:
  • Funciones Puras e Inmutabilidad: Funciones que ante los mismos parámetros siempre producen el mismo resultado sin efectos secundarios externos.
  • Geometría Computacional Básica: Modelado sobre el elipsoide WGS84 para calcular distancias geodésicas ortogonales entre un incidente y la línea de la vía.
  • Complejidad Temporal: Algoritmos diseñados para evaluar tramos e incidentes en tiempo lineal $O(N)$ sin ciclos anidados costosos.

Tecnologías y Módulos Oficiales

Tecnología Propósito en la Capa
TypeScript Definición rigurosa de modelos inmutables (Ruta, Tramo, Incidente) y contratos de interfaces.
@turf/turf Algoritmos geodésicos para medir distancias sobre la superficie terrestre e intersección de radios de afectación.
date-fns Aritmética de tiempo determinista y cálculo de diferencias horarias en zona de Colombia (UTC-5).
Patrones de Código Limpio (Clean Code Patterns):
  • Principio de Responsabilidad Única (SRP): Cada caso de uso resuelve una sola tarea (ej. CalcularRetrasoRutaUseCase.ts).
  • Inversión de Dependencias (DIP): La lógica no se acopla a la base de datos real; define interfaces abstractas (ej. IRutaRepository.ts) que la Capa 3 implementa.
  • Objetos de Valor (Value Objects): Tipos inmutables auto-validados (ej. CoordenadaGPS con rangos válidos de latitud y longitud).
Capa 3: Datos e Infraestructura (Persistencia y Red)

1. Responsabilidad de la Capa

Es la encargada de comunicarse con el mundo exterior: la base de datos local SQLite en el teléfono, los chips GNSS (GPS), el enclave seguro del hardware y los servidores web de INVIAS y datos abiertos del Estado. Tiene prohibido tomar decisiones sobre reglas de negocio.

Conceptos Teóricos para Principiantes:
  • Propiedades ACID en Bases de Datos: Atomicidad, Consistencia, Aislamiento y Durabilidad. Si el teléfono se apaga de golpe, la transacción se revierte y la base de datos no se corrompe.
  • Búsquedas B-Tree vs. Búsquedas Secuenciales: Un índice en SQLite permite búsquedas logarítmicas $O(\log N)$ en lugar de recorrer toda la tabla $O(N)$.
  • Gestión de Procesos en Segundo Plano: Los sistemas operativos móviles suspenden apps inactivas para ahorrar energía. Se requiere un *Foreground Service* nativo para telemetría.

Tecnologías y Módulos Oficiales

Tecnología Propósito en la Capa
expo-sqlite Motor relacional embebido local para garantizar operatividad 100% Offline-First.
expo-secure-store Cifrado en hardware usando Android Keystore y iOS Keychain para tokens de sesión.
expo-location + expo-task-manager Captura periódica de coordenadas GPS registradas ante el kernel del sistema operativo.
@tanstack/react-query Caché asíncrona, deduplicación de consultas y reintentos automáticos con retroceso exponencial.
@react-native-community/netinfo Detección de conectividad de red celular/WiFi para disparar sincronizaciones diferidas.
Patrones de Código Limpio (Clean Code Patterns):
  • Patrón Repositorio (Repository Pattern): Abstrae el origen de la información. La app solicita una ruta y el repositorio decide si la lee de SQLite o la descarga de internet.
  • Patrón Adaptador / Mapeador (Adapter / Mapper): Limpia y transforma los GeoJSON de ArcGIS de INVIAS en objetos limpios de dominio.
  • Data Transfer Object (DTO): Contratos de datos de entrada/salida de red aislados del modelo de base de datos.

4. Modelo de Datos Relacional (SQLite DDL en Capa 3)

-- 1. Usuarios / Conductores
CREATE TABLE IF NOT EXISTS usuarios (
    id TEXT PRIMARY KEY,
    nombre TEXT NOT NULL,
    documento TEXT NOT NULL UNIQUE,
    rol TEXT CHECK(rol IN ('conductor', 'operador', 'consulta')) DEFAULT 'conductor',
    token_sesion TEXT,
    creado_en DATETIME DEFAULT CURRENT_TIMESTAMP
);

-- 2. Rutas Planificadas
CREATE TABLE IF NOT EXISTS rutas_entrega (
    id TEXT PRIMARY KEY,
    usuario_id TEXT NOT NULL,
    codigo_manifiesto TEXT,
    origen_nombre TEXT NOT NULL,
    origen_lat REAL NOT NULL,
    origen_lon REAL NOT NULL,
    destino_nombre TEXT NOT NULL,
    destino_lat REAL NOT NULL,
    destino_lon REAL NOT NULL,
    eta_pactado DATETIME NOT NULL,
    eta_recalculado DATETIME,
    distancia_total_km REAL NOT NULL,
    tiempo_estimado_base_min INTEGER NOT NULL,
    estado TEXT CHECK(estado IN ('pendiente', 'en_ruta', 'completada', 'retrasada', 'cancelada')) DEFAULT 'pendiente',
    creado_en DATETIME DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (usuario_id) REFERENCES usuarios(id) ON DELETE CASCADE
);

-- 3. Segmentos de la Ruta
CREATE TABLE IF NOT EXISTS tramos_ruta (
    id TEXT PRIMARY KEY,
    ruta_id TEXT NOT NULL,
    orden_secuencia INTEGER NOT NULL,
    origen_segmento_lat REAL NOT NULL,
    origen_segmento_lon REAL NOT NULL,
    destino_segmento_lat REAL NOT NULL,
    destino_segmento_lon REAL NOT NULL,
    via_codigo TEXT,
    distancia_km REAL NOT NULL,
    tiempo_base_min INTEGER NOT NULL,
    FOREIGN KEY (ruta_id) REFERENCES rutas_entrega(id) ON DELETE CASCADE
);

-- 4. Incidentes y Estado Vial
CREATE TABLE IF NOT EXISTS incidentes_viales (
    id TEXT PRIMARY KEY,
    id_fuente_externa TEXT,
    tipo_evento TEXT CHECK(tipo_evento IN ('cierre_total', 'paso_a_un_carril', 'derrumbe', 'mantenimiento', 'accidente', 'clima', 'manifestacion')) NOT NULL,
    gravedad TEXT CHECK(gravedad IN ('baja', 'media', 'alta', 'critica')) NOT NULL,
    descripcion TEXT,
    via_codigo TEXT,
    ubicacion_lat REAL NOT NULL,
    ubicacion_lon REAL NOT NULL,
    radio_afectacion_km REAL DEFAULT 1.0,
    retraso_estimado_min INTEGER DEFAULT 0,
    fuente TEXT NOT NULL,
    estado TEXT CHECK(estado IN ('activo', 'resuelto', 'verificado')) DEFAULT 'activo',
    fecha_reporte DATETIME NOT NULL,
    actualizado_en DATETIME DEFAULT CURRENT_TIMESTAMP
);

-- 5. Búfer de Telemetría GPS Local
CREATE TABLE IF NOT EXISTS telemetria_puntos (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    ruta_id TEXT NOT NULL,
    latitud REAL NOT NULL,
    longitud REAL NOT NULL,
    velocidad_kmh REAL,
    altitud REAL,
    bateria_nivel REAL,
    timestamp_captura DATETIME NOT NULL,
    sincronizado INTEGER DEFAULT 0,
    FOREIGN KEY (ruta_id) REFERENCES rutas_entrega(id) ON DELETE CASCADE
);

-- 6. Historial de Evaluaciones de Retraso
CREATE TABLE IF NOT EXISTS evaluaciones_retraso (
    id TEXT PRIMARY KEY,
    ruta_id TEXT NOT NULL,
    incidente_id TEXT,
    retraso_delta_min INTEGER NOT NULL,
    causa_principal TEXT NOT NULL,
    timestamp_calculo DATETIME DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (ruta_id) REFERENCES rutas_entrega(id) ON DELETE CASCADE,
    FOREIGN KEY (incidente_id) REFERENCES incidentes_viales(id) ON DELETE SET NULL
);

-- Índices B-Tree Estratégicos
CREATE INDEX IF NOT EXISTS idx_telemetria_sync ON telemetria_puntos(ruta_id, sincronizado);
CREATE INDEX IF NOT EXISTS idx_incidentes_espacial ON incidentes_viales(ubicacion_lat, ubicacion_lon, estado);
CREATE INDEX IF NOT EXISTS idx_tramos_orden ON tramos_ruta(ruta_id, orden_secuencia);
CREATE INDEX IF NOT EXISTS idx_rutas_estado ON rutas_entrega(usuario_id, estado);

5. Catálogo de APIs y Fuentes Viales de Colombia (Capa 3)

  • Portal de Datos Abiertos (datos.gov.co): Socrata Open Data API (SODA). Inventario de vías primarias y peajes concesionados para precargar la base de datos local.
  • Geoportal INVIAS / Sistema HERMES: ArcGIS REST Services. Reportes oficiales en tiempo real del #767 (cierres totales, pasos a un carril y derrumbes).
  • Alertas Hidrometeorológicas del IDEAM: Servicios WMS/GeoJSON con niveles de amenaza por remoción en masa en zonas de cordillera.
  • OpenStreetMap (OSM) / OSRM: Trazado de la polilínea de la ruta base origen-destino sin incurrir en costos de licencias comerciales.
  • TomTom / HERE Traffic API: Medición de velocidades y demoras dinámicas por congestión en tiempo real.

6. Motor Matemático de Cálculo de Retraso (Capa 2)

ETA_recalculado = Tiempo_actual + Σ(T_tramo_i) + Σ(D_incidente_j)
ΔT = ETA_recalculado - ETA_pactado

Donde el retraso $\Delta T > 0$ se clasifica en minutos e informa proactivamente a la logística de transporte si el envío llegará a tiempo.
